# قرارداد انتقال دستگاه‌به‌دستگاه ساعت‌یار

این سند قرارداد فاز ۱۱۳ را برای Transportهای آینده تعریف می‌کند. لایه انتقال نباید به QR، WebRTC یا سرور خاصی وابسته باشد.

## چرخه پیشنهادی

1. دستگاه فرستنده از AppData فعلی یک Payload نسخه‌دار می‌سازد.
2. SHA-256 Payload بررسی‌پذیری خرابی و دست‌کاری را فراهم می‌کند.
3. برای Pairing یک کلید نشست تصادفی ۲۵۶ بیتی ساخته می‌شود.
4. Payload با AES-GCM رمز می‌شود.
5. Transport فاز ۱۱۴ Envelope رمزنگاری‌شده را منتقل می‌کند.
6. مقصد ابتدا رمزگشایی و Checksum را بررسی می‌کند.
7. مقصد Preview تعارض را بدون تغییر داده نشان می‌دهد.
8. کاربر `merge` یا `replace` و در Merge سیاست تعارض را انتخاب می‌کند.
9. فقط بعد از تأیید، AppData جدید به Persistence تحویل داده می‌شود.

## اصل‌های امنیتی

- Secret نشست جزو Payload یا Envelope نیست.
- کلید نشست دائمی نیست و نباید همراه Backup ذخیره شود.
- AES-GCM علاوه بر محرمانگی، صحت ciphertext را نیز بررسی می‌کند.
- Checksum SHA-256 لایه مستقلی برای تشخیص تغییر Payload پس از رمزگشایی است.
- دستگاه با Schema قدیمی‌تر بسته‌ای با Schema جدیدتر را Import نمی‌کند.

## سیاست تعارض

`merge + keep-local` امن‌ترین پیش‌فرض است: داده‌های جدید وارد می‌شوند ولی مقادیر هم‌کلید محلی حفظ می‌شوند.

`merge + use-incoming` برای انتقال کنترل از دستگاه دیگر مناسب است و تعارض‌های هم‌کلید را با نسخه ورودی جایگزین می‌کند.

`replace` باید در UI با هشدار واضح نمایش داده شود چون کل AppData مقصد را با داده دریافتی جایگزین می‌کند.

## Pairing Transport — Phase 114

پروتکل انتقال به Transport وابسته نیست. فاز ۱۱۴ یک Transport مستقیم WebRTC اضافه می‌کند:

- `RTCPeerConnection` بدون Signaling server دائمی
- Offer/Answer نسخه‌دار با `saatyar-device-pair:v1`
- Pairing Code یا لینک دارای Fragment برای تبادل دستی Signaling
- Session key همان نشست داخل Offer و دارای عمر کوتاه
- DataChannel ordered با Chunking و ACK
- بهترین عملکرد در یک شبکه Wi-Fi مشترک

QR صرفاً یک روش نمایش همین Pairing Code خواهد بود و در فاز بعد بدون API شخص ثالث اضافه می‌شود.
