# راهنمای جامع Agentهای توسعه ساعت‌یار

این سند برای Agentهای کدنویسی، Maintainerها و مشارکت‌کنندگانی است که می‌خواهند بدون شکستن معماری و داده‌های کاربران روی ساعت‌یار کار کنند.

## ۱. مدل ذهنی محصول

ساعت‌یار یک وب‌اپ فارسی، RTL و Local-first برای ثبت زمان، محاسبه کارکرد، حقوق، پروژه و گزارش است. داده اصلی کاربر در مرورگر نگهداری می‌شود؛ بنابراین سازگاری Schema، Backup و Migration بخشی از قرارداد محصول است، نه جزئیات پیاده‌سازی.

حالت‌های اصلی محصول:

- کارمند
- فریلنسر
- ترکیبی

مسیرهای اصلی:

- `/today`
- `/month`
- `/leave`
- `/reports`
- `/clients`
- `/projects`
- `/invoices`
- `/settings`

## ۲. ترتیب مطالعه مخزن

برای شروع این فایل‌ها را به‌ترتیب بخوان:

1. `README.md`
2. `AGENTS.md`
3. `docs/roadmap/BACKLOG_FA.md`
4. آخرین یادداشت فاز در `docs/phases/`
5. تست‌های مرتبط با حوزه تغییر
6. فایل مالک رفتار و helperهای دامنه آن

## ۳. معماری و مالکیت رفتار

- منطق محاسباتی باید در `lib/` یا helperهای خالص باشد.
- صفحه‌ها orchestration انجام دهند و منطق بزرگ را به component/hook/domain helper بسپارند.
- تست معماری باید مالک واقعی رفتار را بررسی کند؛ به نام تابع داخلی که ممکن است با Refactor حذف شود وابسته نشود.
- هر فایل UI یا hook که به ۲۵۰ خط نزدیک شد باید قبل از رشد بیشتر شکسته شود.
- Import محلی جدید باید با `npm run check:imports` بررسی شود.

## ۴. سیاست کامپوننت و shadcn/ui

برای نیازهای عمومی مانند Dialog، Alert Dialog، Dropdown، Tabs، Tooltip، Popover، Form، Toast و Sheet:

1. ابتدا بررسی کن آیا نمونه رسمی shadcn/ui مناسب وجود دارد.
2. آن را با CLI رسمی پروژه نصب کن.
3. خروجی را داخل `components/ui/` با توکن‌های پروژه سفارشی کن.
4. RTL، صفحه‌کلید، focus، تم روشن/تاریک و Responsive را تست کن.
5. API کامپوننت را تا جای ممکن نزدیک shadcn نگه دار تا نگهداری و ارتقا ساده بماند.

نمونه دستور:

```bash
npx shadcn@latest add alert-dialog
```

نسخه دست‌ساز جدید فقط وقتی مجاز است که shadcn کامپوننت مناسب نداشته باشد یا نیاز محصول ذاتاً اختصاصی باشد. دلیل این تصمیم باید در یادداشت فاز نوشته شود.

## ۵. تنظیمات و Draft

وقتی `autoSaveSettings` خاموش است:

- کارت ابتدا فقط خواندنی است.
- دکمه مداد وارد حالت ویرایش می‌شود.
- تغییرات داخل Draft می‌مانند.
- ذخیره، Draft را Commit می‌کند.
- انصراف، Draft را دور می‌ریزد.
- جابه‌جایی یا خروج با تغییر ذخیره‌نشده باید هشدار معتبر داشته باشد.

وقتی ذخیره خودکار روشن است، تغییرات می‌توانند مستقیم اعمال شوند اما باید خطای ذخیره و وضعیت آخرین ذخیره قابل مشاهده باشد.

## ۶. داده، Schema و Migration

هر تغییر پایدار در `AppData` یا `Settings` نیازمند بررسی این موارد است:

- افزایش نسخه Schema در صورت نیاز
- مقدار پیش‌فرض
- Migration داده قدیمی
- Backup validation
- Recovery snapshot
- تست round-trip
- ردکردن نسخه جدیدتر ناشناخته

فیلد اختیاری نیز باید از نظر Backup و Migration آگاهانه بررسی شود؛ اختیاری‌بودن به‌تنهایی تضمین سازگاری نیست.

## ۷. زمان و نشست کاری

زمان‌های ساعت‌محور و Timestampهای مطلق را مخلوط نکن. رکورد دستی همان روز باید بر اساس ساعت‌های همان روز محاسبه شود. نشست باز، Crash، Refresh، چند Tab و عبور از نیمه‌شب سناریوهای جدا هستند و برای هرکدام تست لازم است.

## ۸. UI، تم و دسترس‌پذیری

- فقط از Semantic tokens مانند `--surface-1`، `--text`، `--border`، `--accent` و توکن‌های وضعیت استفاده کن.
- رنگ ثابت `bg-white`، `text-black` یا رنگ‌های وضعیت Tailwind در بخش‌های audited ممنوع است.
- UI باید با صفحه‌کلید، focus visible و reduced motion سازگار باشد.
- Dialog و Picker باید نام قابل‌دسترسی، focus trap و Escape داشته باشند.
- موبایل، دسکتاپ، RTL و هر دو تم را بررسی کن.

## ۹. تست و کنترل کیفیت

حداقل اجرای لازم:

```bash
npm run check:imports
npm run typecheck
npm run lint
npm test
npm run build:vercel
```

اجرای استاندارد:

```bash
npm run check:quality
```

برای هر باگ، ابتدا یک تست Regression بنویس که سناریوی واقعی را بازتولید کند. تست‌های متنی معماری باید رفتار پایدار را بررسی کنند، نه چینش اتفاقی JSX یا نام داخلی تابع.

## ۱۰. مستندات فاز

برای هر فاز فایل زیر را بساز:

```text
docs/phases/PHASE_<NUMBER>_NOTES_FA.md
```

محتوا:

- مسئله و علت
- تغییرات اصلی
- فایل‌های مهم
- تصمیم‌های معماری
- Migration و Dependency
- تست‌های اجراشده
- محدودیت‌های باقی‌مانده
- پیام Commit پیشنهادی

بک‌لاگ فقط در `docs/roadmap/BACKLOG_FA.md` به‌روزرسانی شود.

## ۱۱. فرایند پیشنهادی Agent

1. وضعیت Git و آخرین فاز را بررسی کن.
2. حوزه تغییر و مالک رفتار را مشخص کن.
3. تست شکست‌خورده یا Regression را بنویس.
4. کمترین تغییر منسجم را پیاده‌سازی کن.
5. فایل‌های بزرگ را تفکیک کن.
6. مستندات و بک‌لاگ را به‌روزرسانی کن.
7. `npm run check:quality` را اجرا کن.
8. خروجی، محدودیت و Commit پیشنهادی را دقیق گزارش کن.

## ۱۲. کارهایی که Agent نباید انجام دهد

- تغییر Schema بدون Migration و تست
- حذف تست برای عبور از Quality Gate
- ساخت کامپوننت عمومی موازی با shadcn بدون دلیل
- استفاده از رنگ ثابت به‌جای توکن تم
- ذخیره خودکار پنهانی وقتی تنظیم آن خاموش است
- محاسبه زمان چندروزه از یک ساعت دستی
- قرار دادن فایل‌های فاز در ریشه پروژه
- ادعای موفقیت Build بدون اجرای واقعی آن
